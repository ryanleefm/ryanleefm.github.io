记录日期：2026-10-02，Asia/Shanghai。适用于本次已配置的 Windows 与 Zirconium 笔记库。版本和验证状态是记录时的快照，后续升级应重新检查。

快速操作见 用户手册（简略版），错误处理见 故障排查表，维护交接见 Agent 交接说明。

3. 自动同步设置

在每台设备的 Obsidian 中进入“设置 → Git”。设置是每个库、每台设备单独保存的。

英文选项本方案设置作用
Auto commit-and-sync interval (minutes)10定时提交并执行同步
Use separate commit and push intervals关闭使用一组提交同步定时器
Auto push interval (minutes)0不额外启用独立推送定时器
Auto pull interval (minutes)0不额外启用独立拉取定时器
Pull on startup开启打开库时拉取远端
Pull on commit-and-sync开启提交同步流程包含拉取
Push on commit-and-sync开启提交同步流程包含推送

这里的两个独立间隔为 0，不代表整个同步已关闭；整体定时流程由第一项控制。插件名称是 Git，插件目录名为 obsidian-git。

自动任务需要 Obsidian 打开这个库，电脑联网且未休眠。关闭应用后不会继续在后台每 10 分钟执行。插件可能记住定时任务时间，下次打开时执行到期任务；定时运行不是实时协作服务。插件自动任务说明

本机 Linux 使用 Merge 合并，冲突策略为 none，不自动选择某一端的内容。Windows 合并相关选项尚未逐项核验；在更改合并行为前先备份。

4. 每天怎么使用

开始编辑前

  1. 打开本系统的同步库。
  2. 等待启动拉取完成；需要明确检查时打开命令面板，执行 Git: Pull。
  3. 确认没有认证、网络或冲突错误，再开始编辑。
  4. 新库刚接入时，确认测试笔记和预期文档都已出现。

编辑期间

Obsidian 会保存文件，Git 插件按间隔同步。自动同步报错时，本地文件可能仍已保存，但还没有推送到 GitHub；应查看具体错误。

两端可以同时打开，但编辑前都应拉取。尽量避免同时修改同一篇笔记，尤其不要两端同时移动同一文件夹或重命名同一篇笔记。处理不同文件也可能让分支暂时分叉；出现错误按故障排查表处理。

切换电脑、系统或准备关机前

  1. 按 Ctrl+P。
  2. 执行 Git: Commit-and-sync。
  3. 等待完成，并查看是否有错误通知。
  4. 需要确认时运行下面的 Git 状态命令。
  5. 在另一端先拉取，再继续编辑。

不要在刚编辑完时立刻关机，并假定 10 分钟定时器已经运行。

离线工作

本地编辑可以继续。离线期间无法拉取或推送，自动任务可能报网络错误。恢复网络后先检查状态，再执行 Commit-and-sync；两端都离线修改过同一文件时可能需要人工合并。

5. 怎样确认同步成功

Windows PowerShell：

git -C D:\Obsidian-Sync-Git status --short --branch
git -C D:\Obsidian-Sync-Git log -1 --oneline

Zirconium 终端：

git -C /home/rlee/Documents/Obsidian-Sync-Git status --short --branch
git -C /home/rlee/Documents/Obsidian-Sync-Git log -1 --oneline
输出含义
只有 main…origin/main，没有文件行工作区干净，与本地记录的远端分支一致
M 文件名已跟踪文件有未提交修改
?? 文件名新文件尚未加入 Git
ahead N有本地提交尚未推送
behind N本地记录的远端分支领先
ahead N, behind M两端提交历史已分叉，需要检查后合并
UU 或 unmerged存在冲突

origin/main 是本地缓存，状态干净不能独立证明 GitHub 当前没有更新。需要严格验证时先完成备份，再 fetch 获取最新远端信息，或者在 GitHub 查看提交。fetch 更新远端记录，不直接改写笔记工作区。另一台设备成功拉取并显示相同提交，是更完整的跨设备证据。

6. 暂停和恢复自动同步

暂停

先记录当前设置。将自动提交、独立推送和独立拉取间隔全部改为 0，关闭 Pull on startup。暂停后不要主动运行 Pull 或 Commit-and-sync，直到完成检查。

导入原笔记、处理冲突、恢复历史文件时，先暂停相关设备的同步。更稳妥的做法是关闭另一端正在使用此库的 Obsidian。

恢复

恢复第 3 节中的设置。处理冲突或导入后先完成一次手动同步，并在另一端确认结果，再恢复定时任务。

插件的 data.json 可能在首次修改设置前尚未生成。缺少该文件不等于插件安装失败。备份整个 .obsidian 目录即可包含已经存在的配置。

7. 如何备份

备份放在同步库外，保留完整目录，包括隐藏的 .git 与 .obsidian。GitHub 历史有助于恢复已提交内容，但未提交文件、未推送提交及设备配置仍需要本地备份。

Windows 新同步库备份

先关闭这个库的 Obsidian 窗口，再执行整个代码块。任一步失败都会停止该代码块：

& {
    $ErrorActionPreference = 'Stop'
    $vaultBackup = 'D:\Obsidian-Sync-Backups\manual-' + [guid]::NewGuid().ToString('N')
    New-Item -ItemType Directory -Path $vaultBackup | Out-Null
    Copy-Item -LiteralPath 'D:\Obsidian-Sync-Git' -Destination $vaultBackup -Recurse -Force
    git -C "$vaultBackup\Obsidian-Sync-Git" fsck --full
    if ($LASTEXITCODE -ne 0) { throw '备份 Git 完整性检查失败' }
    Write-Host "备份目录：$vaultBackup"
}

fsck 检查 Git 对象，不会验证未跟踪文件或所有 .obsidian 设置。重要备份还应确认笔记、附件和配置存在，并比较文件数量、大小或哈希。Windows 原笔记库必须用它自己的实际路径另行备份，不能拿新库备份替代。

Linux 新同步库备份

先关闭这个库的 Obsidian，再执行整个代码块。子 shell 中任一步失败就停止，不影响终端本身：

(
    set -eu
    vaultBackupDir="$(mktemp -d /home/rlee/Documents/Obsidian-Sync-Backups/manual-XXXXXXXX)"
    tar -czf "$vaultBackupDir/vault.tar.gz" -C /home/rlee/Documents Obsidian-Sync-Git
    tar -tzf "$vaultBackupDir/vault.tar.gz"
)

确认每一步成功。最后一条只检查压缩包能否列出内容；对重要备份再做逐文件哈希核验。恢复时先解压到新的目录，比较内容后再决定是否替换，避免直接覆盖正在使用的库。

8. 导入 Windows 原始笔记

当前尚未执行这一步。导入前：

  1. 确定原笔记库的实际路径，确认它是数据源。
  2. 关闭原库，完整备份原库；保留原目录和旧 Git 历史。
  3. 备份新同步库，暂停新库的自动任务，并让另一端暂时关闭此库。
  4. 在新库拉取最新内容，确认没有未处理冲突。
  5. 复制笔记、Canvas 与附件。保留新库的 .git、.gitignore、.gitattributes，不复制旧库的 .git、.obsidian、.trash。
  6. 遇到同名文件先比较，不能直接覆盖。保留冲突副本再人工决定。
  7. 检查上传文件列表和内容，排除真实凭据、恢复码及不希望同步的私人资料。原库可能有工作资料，需要逐项决定是否上传到这个私有仓库。
  8. 人工提交并推送，另一端拉取核验笔记数量、附件链接和中文显示。
  9. 确认成功后恢复自动同步。

导入保留的是内容；旧 Windows 仓库的历史仍留在旧库和备份里，新同步库不会自动继承它。需要迁移旧历史时另行设计方案。

9. 哪些内容会同步

会同步：未被忽略的 Markdown、Canvas、附件，以及本文件夹的四份文档。

默认不提交：

  • .obsidian/：插件、界面和字体设置；
  • .trash/、系统杂项、编辑器状态和临时文件；
  • .env、.env.*、常见密钥文件和凭据目录；
  • 库内名为 Obsidian-Sync-Backups 的目录。

.env.example 被允许跟踪，只能放无真实秘密的示例。忽略规则不会自动移除早已跟踪的文件，也不能识别写在普通 Markdown 中的密码。完整规则以库根目录的 .gitignore 为准。

文本文件使用 LF；换行提醒通常不代表中文编码损坏。二进制附件保持原格式。

大型附件应先评估。GitHub 对大于 50 MiB 的文件发出警告，普通 Git 上传会阻止大于 100 MiB 的文件。本项目尚未配置 Git LFS；遇到超限文件时暂停提交并设计附件存储方案。GitHub 文件大小说明

10. 认证与 2FA

Linux 通过 Flatpak 自带的 GitHub CLI 进行 OAuth 登录，当前凭据保存在系统密钥环。Windows 使用 Git Credential Manager；不需要把 Linux 的认证文件复制过去。

启用 GitHub 2FA 通常不要求重建 Git 仓库。OAuth/GCM 认证与网页密码登录不同，重新授权时按浏览器要求完成二次验证；令牌撤销、权限变化或凭据失效仍可能要求重新登录。GitHub 2FA 认证说明

不要把令牌写进远端 URL、Markdown、Git 配置截图或交接文档。出现异常登录地点时先核对自己是否正在授权；学校网络出口可能与所在地不同，但不能只凭这个可能性认定任何授权都是安全的。

Linux 确认需要重新授权时，在自己的终端运行：

flatpak run --command=gh md.obsidian.Obsidian auth login --hostname github.com --git-protocol https --web

保留现有仓库本地 helper；如询问是否同时配置 Git 认证，可选 No，继续完成网页授权。网页成功后回到终端确认流程完成，不把设备授权码或凭据发给别人。Windows 使用 GCM 的浏览器授权提示。GitHub CLI 登录说明

11. 中文显示和设备迁移

Linux 的 Obsidian 专用字体位于：

/home/rlee/.var/app/md.obsidian.Obsidian/data/fonts/obsidian-cjk

界面和正文使用 Noto Sans CJK SC，代码字体使用 Noto Sans Mono CJK SC。修复后曾因旧主进程仍在运行而未立即生效，完整退出所有 Obsidian 窗口再启动后已正常显示。

字体目录与 .obsidian 不进入 Git。因此重新安装 Flatpak 或换电脑时，要重新检查字体、Git 与认证。不要把 Linux 的整份 .obsidian 复制到 Windows，以免携带 Linux 路径或字体名称。

插件更新应逐端操作：备份配置，更新后检查插件兼容性，手动拉取和推送测试通过后再恢复自动任务。插件安装说明

12. 恢复旧内容与更换设备

恢复一篇笔记时，先暂停同步并备份。通过命令面板 Git: Open history view 查看目标笔记的历史，把需要的旧内容复制到新的恢复笔记，比较后再更新当前笔记并提交。附件先恢复到库外目录再比较，避免覆盖。Git 历史只能恢复曾经提交的内容；未提交内容优先找本地备份或回收站。插件历史视图说明
