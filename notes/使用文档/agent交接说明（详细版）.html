Obsidian Git 同步 Agent 交接说明（详细版）

记录日期：2026-10-02，Asia/Shanghai。本文是维护交底，不是对未来操作的无限授权。接手时以用户最新指令和实际状态为准。

关联文档：详细用户手册、简略手册、故障排查表、新电脑接入指南。

1. 用户目标与执行边界

用户要让 Zirconium 与 Windows 的 Obsidian 库通过 GitHub 私有仓库同步。Windows 原库是原始数据源；Linux 初始 Obsidian Vault 没有有价值内容。新同步库命名 Obsidian-Sync-Git。

用户要求：

  • 分阶段执行，重要阶段解释结果并确认后继续；
  • 任何修改前先完成备份；
  • 不经确认不得删除或覆盖原始笔记；
  • 不得把私人笔记上传到公开仓库；
  • 不得提交密码、令牌、恢复码等敏感信息；
  • 检查 Flatpak 权限、插件兼容性，先手动测试再开自动任务。

用户曾允许重命名或删除 Linux 初始空库，但实际选择了保留旧库、创建新库。接手者不应把这次许可泛化为允许删除未来包含数据的目录。

本次已获授权：创建私有仓库、配置新库、安装插件、备份、中文字体修复、测试笔记同步，以及在新库中新建本文件夹和四份初始文档，后续另授权新增 Windows/Linux 新电脑接入指南。Windows 设置由用户亲自执行并反馈；当前 agent 没有 Windows 远程终端。

3. GitHub 仓库与 Git 配置

  • 仓库：https://github.com/ryanleefm/Obsidian-Sync-Git
  • origin：https://github.com/ryanleefm/Obsidian-Sync-Git.git
  • owner/签名用户名：ryanleefm
  • commit email：ryanleefm@gmail.com
  • 分支：main，跟踪 origin/main
  • 私有性：创建时及跨系统推送前均通过 gh repo view 验证 PRIVATE。

Linux 仓库本地配置：

user.name=ryanleefm
user.email=ryanleefm@gmail.com
core.autocrlf=false
core.safecrlf=warn
pull.ff=only
push.default=simple
fetch.prune=true

Windows 已提供同样的设置命令，用户继续完成插件与测试；这些值未逐项远程核验。配置只作用于同步库，不依赖改写全局 Git 配置。

Linux 针对 https://github.com 的 credential helper：第一个值为空，重置继承的 helper；第二个值为下列函数，使用应用内 gh，宿主缺少 gh 时转入 Flatpak：

!f() { if command -v gh >/dev/null 2>&1; then gh auth git-credential "$@"; else flatpak run --command=gh md.obsidian.Obsidian auth git-credential "$@"; fi; }; f

这是程序调用逻辑，没有凭据。不要直接把 Linux 仓库整个 .git 复制到 Windows，避免覆盖 Windows 的对象、分支与认证设置。Windows 使用它自己的 GCM。

pull.ff=only 约束 git pull；插件的 Merge 实现可能执行 fetch 后 git merge，并不因此获得同样的快进限制。不要声称此配置保证插件永不产生合并提交。

4. 忽略规则与文件格式

根 .gitignore 忽略整个 .obsidian/、.trash/、系统文件、编辑器临时状态、常见凭据目录与文件，并忽略 Obsidian-Sync-Backups/。

.env.example 是允许跟踪的例外。插件、字体设定、自动任务设置不随 Git 传到 Windows。使用文档文件夹的 Markdown 会随定时同步上传到当前私有仓库。

.gitattributes 内容：

* text=auto
*.md text eol=lf
*.canvas text eol=lf

忽略规则不能阻止早已跟踪的文件，也不能识别正文中的秘密。导入时要检查文件内容和暂存清单，而不是只检查扩展名。

5. 认证与隐私

Linux 宿主最初没有 gh；Flatpak 内已有 gh、Git、SSH。Flatpak 原有权限提供 home 访问、网络和 ssh-auth socket，本次没有扩展权限。

GitHub 认证由用户亲自完成网页登录。凭据存于密钥环。应用 gh 配置位置：

/home/rlee/.var/app/md.obsidian.Obsidian/config/gh/hosts.yml

先前检查权限为 0600，未含明文 oauth_token。只记录这一结论，接手时不要把文件全文写进工具输出、日志或笔记。

曾出现 GitHub 提示授权来源为 Ireland；用户声明未开启代理、使用能访问 Google 的学校 WiFi。已解释上游出口/地理定位是可能原因，但没有证明这一网络路径。不要沿用精确旧 IP 作为当前信任依据。

用户问过今后启用 2FA 是否影响成果。结论：通常不需要重建现有 OAuth/GCM 同步，重新授权时按网页要求完成二次验证，凭据撤销或权限变更除外。GitHub 官方说明

只读认证检查可用 gh auth status。禁止输出 gh auth token、git credential fill 的密码字段、密钥环内容，禁止把令牌嵌入 origin URL。

Linux 文件：

.obsidian/plugins/obsidian-git/manifest.json
.obsidian/plugins/obsidian-git/data.json
.obsidian/community-plugins.json

已安装 Git 2.41.0，community-plugins 启用 obsidian-git。核心设置现场复核：

{
  "autoSaveInterval": 10,
  "autoPushInterval": 0,
  "autoPullInterval": 0,
  "autoPullOnBoot": true,
  "differentIntervalCommitAndPush": false,
  "pullBeforePush": true,
  "disablePush": false,
  "syncMethod": "merge",
  "mergeStrategy": "none",
  "autoBackupAfterFileChange": false,
  "limitToVault": true
}

Linux 提交消息为 vault sync: {{date}}，Windows 默认消息曾为 vault backup: 时间。消息名不同不影响同步。

Windows 用户确认已经按 10 分钟、独立间隔关闭、启动拉取及提交同步时拉取推送开启配置。尚未直接读取 Windows data.json，其他设置不可视为已逐项验证。

Windows 最初 data.json 不存在，备份单文件时报错。改为备份整个 .obsidian，用户报告 manifest.json 的 Test-Path 为 true，然后完成自动设置。该结果验证指定插件文件存在，不等同于对备份内所有文件做哈希核验。

8. 中文显示修复完整背景

症状：Flatpak Obsidian 的中文界面或正文显示方框、空白、缺字。用户明确不是输入法问题。

诊断：

  1. 宿主有 Noto CJK 字体，宿主 fc-match 中文正常。
  2. Flatpak 初始 fc-list :lang=zh 为空，中文匹配到 DejaVu。
  3. /run/host/fonts 可见且 TTC 可扫描，但宿主字体映射/缓存仍未让新进程正常匹配 CJK。
  4. 重建宿主路径字体缓存未修复。
  5. 将系统原有的两份字体复制到应用专用 XDG_DATA_HOME/fonts 路径并建立缓存，字体匹配和字符覆盖检查通过。
  6. 界面仍异常时发现旧主进程自 15:44 起一直运行；只关闭或重新打开单个库窗口没有结束主进程。
  7. 备份两个库后正常终止已核验的旧主进程并重启，实际设置界面和笔记截图、渲染器字体证据均正常；用户最终确认生效。

字体原文件：

/usr/share/fonts/google-noto-sans-cjk-vf-fonts/NotoSansCJK-VF.ttc
/usr/share/fonts/google-noto-sans-mono-cjk-vf-fonts/NotoSansMonoCJK-VF.ttc

应用副本：

/home/rlee/.var/app/md.obsidian.Obsidian/data/fonts/obsidian-cjk/NotoSansCJK-VF.ttc
/home/rlee/.var/app/md.obsidian.Obsidian/data/fonts/obsidian-cjk/NotoSansMonoCJK-VF.ttc

两份副本均与系统文件哈希一致，没有修改系统字体，没有下载安装第三方字体，没有修改笔记编码。

同步库 appearance.json：

{
  "interfaceFontFamily": "Noto Sans CJK SC",
  "textFontFamily": "Noto Sans CJK SC",
  "monospaceFontFamily": "Noto Sans Mono CJK SC"
}

曾临时启用仅 localhost 的远程调试端口 9227 获取字体和截图证据，随后关闭并恢复普通启动，已核验端口不再监听。不要默认重新开启调试；该接口可读取笔记内容。

字体修复时暂停过自动任务，但用户之后已恢复 10 分钟，且现场复核和 1c3fbba 提交证明恢复。font-fix-result.json 中 automatic_sync_paused=true 是那次历史报告，不能当作当前状态。

10. 接手后的第一轮检查

  1. 阅读最新用户请求，明确是在维护、导入还是故障恢复，不重新执行已完成的设备授权。
  2. 核对同步库路径和 Git 顶层目录，确保不操作父工作区仓库。
  3. 只读查看 status、最近提交、origin、插件版本及非敏感设置。
  4. 网络推送前再次核对仓库是 PRIVATE，且 origin 指向预期仓库。
  5. 如需修改，先在库外备份，验证备份可读；未提交内容与 .obsidian 也要保留。
  6. 本机能检查 Linux；Windows 需要让用户提供最小命令输出，不能假装已直接执行。
  7. 每个重要阶段说明结果和不确定性，再按用户的分阶段要求继续。

Linux 最小检查：

git -C /home/rlee/Documents/Obsidian-Sync-Git rev-parse --show-toplevel
git -C /home/rlee/Documents/Obsidian-Sync-Git status --short --branch
git -C /home/rlee/Documents/Obsidian-Sync-Git log -5 --oneline
git -C /home/rlee/Documents/Obsidian-Sync-Git remote get-url origin
flatpak run --command=gh md.obsidian.Obsidian repo view ryanleefm/Obsidian-Sync-Git --json nameWithOwner,isPrivate,visibility

本次执行环境对 Documents 外写入和网络有限制；Flatpak 在沙箱中曾报 Unable to allocate instance id。后续 agent 应遵循当时实际权限机制，必要时申请有明确用途的升级，不绕过限制。普通文档和库外 Documents 备份属于本工作区可写范围。

本次插件源与安装验证材料曾放在 /tmp/obsidian-git-2.41.0-source 和 /tmp/obsidian-git-2.41.0-verified，临时目录可能消失，不依赖其永久存在。
